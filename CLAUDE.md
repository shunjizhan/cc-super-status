# CLAUDE.md — cc-super-status

Guidance for working in this repo. User-facing docs are in `README.md`; this file is the engineering contract.

## What this is

A Claude Code `statusLine` command. Claude Code pipes a JSON blob on stdin every ~5s (and on events); whatever this prints to stdout becomes the user's status line:

```
🥷 Opus 4.8 (xhigh) | 🔥 $13.18/hr | ⭐️ {50}300t/s 3[7] | 💰 $13.5 / $31 / $330 | ⚡ 42m 53% ▰▰▰▰▰▰▰▰▰▰▱▱▱▱▱▱▱▱▱▱
```

It is wired in via `~/.claude/settings.json` → `statusLine.command` (currently `/opt/homebrew/bin/bun run <repo>/statusline.ts`). It **replaced** an older bash script (`~/.claude/ccusage-statusline.sh`, now deleted).

## Runtime & commands

- **Bun only** (committed). `bun run` executes TypeScript directly — there is **no build step**. Don't add one.
- `bun test` — unit + e2e suite. `bun install` — pulls `@types/bun` (type-checking only; tests run without it).
- Edits to `.ts` are live on the next status-line tick; no compile.

## Architecture — pure core, impure shell

Keep the pure/impure split. Pure modules have unit tests; impure I/O is thin and exercised by the e2e + live diffs.

| File | Purity | Responsibility |
| --- | --- | --- |
| `src/types.ts` | — | **The contract. Read first.** All shared types live here (incl. `SharedSnapshot`, `MergedRateLimits`). |
| `src/config.ts` | pure | `parseConfig(env, barScale)` → `Config` (env → defaults, num/bool coercion; `barScale` sizes the ⚡ bar to the plan). |
| `src/paths.ts` | pure-ish | `stateDir()` — where the `ccss-*` coordination files live (`CCSS_STATE_DIR` override). |
| `src/plan.ts` | mixed | `planBarScale(tier)`/`barScaleForMode(mode, tier)` (pure) + `detectRateLimitTier()` — resolve the ⚡ bar's **layer count** from `CCSS_BAR_MODE` + the plan tier read from `~/.claude.json` (it's **not** on stdin; Max 20x → 4 layers). |
| `src/rate.ts` | pure | `computeRatesBySession(entries, now, windowMs)` → `{all, bySession}` (+ clock-skew guard). |
| `src/format.ts` | pure | model / speed / bar / truecolor / quota string rendering. |
| `src/transcripts.ts` | mixed | `parseTranscriptText`/`sessionOrigin`/`countActive`/`tokenCount` (pure) + `gatherEntries` (disk I/O). |
| `src/ccusage.ts` | mixed | `parseCcusage`/`staleLineStillCurrent`/`shouldSpawnJob`/`buildJobScript` (pure) + `readCcusageLine`/`maybeSpawnCcusageJob` (the detached job). |
| `src/shared.ts` | mixed | `cfgKey`/`decideRole`/`mergeRateLimits`/`buildSnapshot`/`parseSnapshot` (pure) + `resolveSnapshot` (leader/follower coordination I/O). |
| `src/buildStatusline.ts` | pure | orchestrator — composes the final line from a `SharedSnapshot` + stdin. |
| `statusline.ts` | impure | entry point: read stdin, `parseConfig`, `resolveSnapshot`, `buildStatusline`, print. |

`buildStatusline` takes a resolved `SharedSnapshot` + stdin `input` + `now` + config, so the whole render is deterministic and e2e-testable. **Keep it that way** — don't reach for `Date.now()`/`process.env`/`fs` inside the pure modules.

## Non-negotiable invariants

- **Never throw, never print a stack trace.** stdout is the user's status line. `statusline.ts` wraps everything in try/catch and degrades to the resolved snapshot's ccusage line or `''`. Per-segment failures drop only that segment (model + ⭐️ always render; 🔥/💰 drop together only when the snapshot has no usable ccusage line; ⚡ renders from the merged `rate_limits` independently and drops only when no quota source is present).
- **Three clocks, and no render ever waits on the slow one** (see README "Multi-session architecture" — this is the load-bearing design). Data is sourced on three cadences, each sized to its cost: **instant** (🤖 + 💰 session-$, from stdin every tick — free), **5s snapshot** (⭐️ rate/counts + ⚡ bars, from one leader's transcript walk), **30s job** (🔥 + 💰 block/today, from a detached `ccusage` recompute). The 5s + 30s outputs are frozen into a `SharedSnapshot` on disk (`resolveSnapshot` in src/shared.ts) so every open pane renders byte-identical globals per generation.
- **The ccusage recompute is a detached, never-killed background job — never on a render path.** A full recompute over a large `~/.claude/projects` takes 3.6–4.9s (measured; ≥10s under multi-session disk contention) — far past any tick-friendly timeout, and it happens exactly while Claude streams. So `maybeSpawnCcusageJob` (src/ccusage.ts) spawns ONE `sh -c` job — only a leader, only when the shared line is older than `Config.ccusageRefreshSec` (env `CCSS_CCUSAGE_REFRESH`, default 30s) AND no job marker is fresh (`shouldSpawnJob`). The job reads the stdin payload from a file, writes ccusage's stdout to a pid-unique temp file, and — only if non-empty — `mv`s it over the shared line `ccss-ccusage.line` (atomic same-filesystem rename); a marker file rate-limits to one job machine-wide. It is `unref()`'d with detached stdio, so nothing this process does can kill it or truncate its output: **every recompute that starts also lands**, and a failed/empty run leaves the previous good line untouched. Ticks read the line via `readCcusageLine`, which serves it only while ≤10 min old and its own "(X left)" says the 5-hour block hasn't reset (`staleLineStillCurrent`, else the ⚡ fallback lane would show wrong-direction quota). Only a brand-new machine (no line yet) briefly renders without 🔥/💰; cold-start convergence is ~5–6s (job lands in ~1.5s, next leader past the 5s lease bakes it into the snapshot).
- **Multi-session coherence: one leader computes the globals, everyone reads the snapshot.** A claim file whose **mtime is the lease** (`decideRole`, `LEASE_MS` = 5s) elects one leader per ~5s generation; it walks transcripts, merges rate-limits, freezes a `SharedSnapshot` (`cfgKey`-scoped, atomic write), and renders from it. Followers read that frozen snapshot — no walk — so all panes print identical `all`/counts/limits/ccusage for a generation (skew ≤ one generation). A follower's own `cur` is its slice `bySession[session_id]` of the same snapshot (a session absent from `bySession` is idle → cur 0, correct); only when NO usable snapshot exists (none yet, or leadership lapsed >2 leases) does it fall back to a local walk. `session $` stays per-pane (from stdin `cost.total_cost_usd`). A rare double-leader (two ticks both see the lease stale) is wasteful, not incorrect. Don't reintroduce per-pane global recomputation — the whole point is 6×→1×.
- **⚡ session + weekly remaining prefer first-party data, merged across sessions.** Claude Code ≥2.1.132 passes `rate_limits.five_hour` and `rate_limits.seven_day` (each `{used_percentage, resets_at}`) on stdin (Pro/Max only; `resets_at` is epoch **seconds**) — the same numbers `/usage` shows. Every tick contributes its own view into a machine-wide monotone merge (`mergeRateLimits`: later `resets_at` wins, tie → higher `used_percentage`), so an idle leader's stale view can't drag the shared bars back; the snapshot freezes the merged windows. Each present window renders as `<timeLeft> <pct>% <bar>`, space-separated, 5-hour leading weekly — a fighting-game **layered** bar (see `renderLane`/`layerColor` in `src/format.ts`): fixed `config.cells` wide (default 20), stacking `config.layers` colour layers (= the plan `barScale`; Max 20x → 4). `displayPct = pct × layers`, so a full window reads `layers×100%` (400% on Max 20x) and consuming a whole layer drops it a clean 100 (400→300). The bar shows only the current (top-most non-empty) layer's fill; its **colour says which layer you're on**: the base layer (1) is the emerald→amber→red danger reserve (`quotaRgb` of its *own* remaining %), the surplus layers above are static **Aurora** identity colours (cyan→blue→violet). The bar splits into three runs of the same solid `▰` glyph — **colour, not glyph, marks each** (a hollow `▱` renders as an outlined box that reads as a glitch on a light terminal). **`solid = floor(fraction × cells)`** cells are fully held, in the current layer's colour. The next single cell is the **FRONTIER — the one being consumed right now** — a **dimmed** shade of the fill (`dimColor` — desaturated + darkened); it's present until the layer is 100% full (`solid === cells`). The rest is the consumed track: the layer directly beneath **muted** (`dimColor`) so it recedes, or the neutral gray `DIM` on the base (nothing lies under it). Because a cell turns solid only once fully held, the frontier sits one cell past the solid run — a 20-cell base reads 95% → 19 solid + 1 dim frontier + 0 empty, 90% → 18 + 1 + 1, 5% → 1 + 1 + 18, and 100% → 20 solid (no frontier). The `<pct>%` label takes the current layer's colour. 5-hour resets shown to the minute, weekly as `Nd Nh`. The 5-hour window prefers `five_hour` (else the ccusage `$`-block + `CCSS_QUOTA` estimate, the only fallback). **The weekly window is opt-in** (`config.showWeekly`, env `CCSS_WEEKLY`, default off). This lives in `formatQuotaSegment` in `src/format.ts` (gated in `buildStatusline`, sourced from `shared.limits`). Don't re-derive these % from costs when the official numbers are available. **Low-quota warning:** for a 1-layer plan (Pro/5x) this is exactly the pre-layer bar — a single green→amber→red bar, red at <20% remaining. For a multi-layer plan the base stays green until you're into the final reserve, then fades amber→red, so **red now means "last reserve nearly gone"** (≈<5% of total on a 4-layer plan); the earlier telegraph is the layer-colour descent (violet→blue→teal→green). Fill fraction + the red/amber/green thresholds key on each layer's *own* 0–100 remaining, so the warning fires per-layer and is never softened by the scaled `<pct>%`. **Precedence:** the **width** is `config.cells` (env `CCSS_CELLS`, default a flat **20** — a higher tier adds layers, it does not widen the bar); the **layer count** is `barScaleForMode(process.env.CCSS_BAR_MODE, detectRateLimitTier())` (`max`→4 / `default`→1 / `auto` → the tier; Max 20x → 4; 5x / Team / Pro / unknown → 1). The tier is **not** on stdin (only `rate_limits` percentages are) — it's read from `~/.claude.json` `oauthAccount.organizationRateLimitTier` (undocumented; read defensively, any miss → 1 layer). Both `cells` and `layers` are render-only, so `cfgKey` deliberately excludes them — per-pane reads that never fragment the snapshot.
- **Token rate semantics** (don't change without asking — they were deliberately chosen, see the git history / the deep discussion that produced this repo):
  - tokens per message are **charge-weighted by default** (`effectiveRate: true`, env `CCSS_EFFECTIVE`): `input ×1 + output ×5 + cache_creation ×2 (all treated as 1-hour) + cache_read ×0.1` — Anthropic's per-component price ratios vs base input, so the ⭐️ rate tracks cost-equivalent tokens (and can be fractional). With `CCSS_EFFECTIVE=0` every weight is 1 (raw throughput, rendered with 🌟 not ⭐️): `input + output + cache_creation + cache_read`, the same four components ccusage sums for its *total tokens*, so the raw rate agrees with ccusage. `CCSS_CACHE=0` (config `includeCache: false`) drops the two cache terms in either mode. All of this — weights + cache include/exclude — is decided once at parse time in `tokenCount`/`parseTranscriptText`, baked into `TokenEntry.tok`; `rate.ts` never sees the split.
  - **dedup by `message.id`** (transcripts log each message 2–3× — counting all rows over-reports ~3×, which is the bug `ccstatusline`'s speed widget has). Duplicate rows carry identical usage, so max-`tok` dedup is correct regardless of weighting or cache inclusion.
  - window = last `CCSS_WINDOW` seconds (**÷ windowSec**, a true sliding average — not ÷ active-processing-time).
  - window ends at `max(now, latestTs)` so the rate **decays to 0 after the window of idle** — but a timestamp more than `CLOCK_SKEW_MS` (60s) in the future is ignored when computing that end (a corrupt/badly-clocked far-future row must not slide the window past every real entry and zero the rate; a legit slightly-future row from clock skew is still honoured).
  - each entry is tagged with its `session` (`sessionOrigin(path).session`); `computeRatesBySession` returns `{all, bySession}`. A pane's `cur` = `bySession[session_id] ?? 0` — decided at render time, NOT baked into the entry (there is no `current` flag; "current" is per-consumer, since one snapshot serves panes with different sessions). `all ≥ bySession[x]` always (sum dominates, `round` is monotone).
  - format collapses `{cur}all` → `all` when `cur === all`.
- **⭐️ active session / sub-agent counts use file mtime, NOT the token window** — the `<sessions>[<subagents>]` suffix (e.g. `⭐️ {50}300t/s 3[7]`, sessions then sub-agents in brackets) is a *live* concurrency readout, deliberately decoupled from the 120s rate window (a smooth-but-laggy average — wrong clock for "who's working now"). A session/sub-agent is active iff its transcript was written within `CCSS_ACTIVE_WINDOW` seconds (`config.activeWindowSec`, default 15). Mechanism: `gatherEntries` emits a `FileActivity {session, subagent, mtimeMs}` per transcript that produced ≥1 token event (so `journal.jsonl` and other usage-less files are excluded); the pure `countActive(files, now, activeMs)` counts distinct `session` keys (a session groups with its own sub-agents via `sessionOrigin`, so it's counted once — and stays counted while only its sub-agents are busy) and distinct non-null `subagent` keys. The counts are computed by the leader and frozen into the snapshot (so they're global and coherent), then `formatSpeed` **always** appends the suffix — idle renders `0[0]`, never an empty string. This is deliberate: suppressing the suffix at `sessions === 0` made the whole readout blink out from under the following ` | ` (shifting every segment right) whenever a single write gap exceeded the window mid-turn; always-rendering means the numbers ride down to `0[0]` instead, so the layout never jumps. mtime is chosen over completed-message timestamps because it advances on *every* write (messages, tool calls, tool results), so it tracks live work; the trade-off is a single tool call longer than the window makes the counts briefly read `0[0]` mid-turn (raise `CCSS_ACTIVE_WINDOW` to 30–45s if it matters). **Needs `refreshInterval` in settings** (currently `5`) to decay the counts on-screen while the main session idles on background sub-agents — those quiet periods fire no events, so the timer is what re-runs the line.
- **ccusage is wrapped, not reimplemented.** It has no JS library API — we shell to `ccusage statusline` and parse its string. Don't try to recompute cost/pricing ourselves.
- **Performance: the heavy walk is leader-only, and it READS only recent transcripts.** `gatherEntries` *enumerates* the whole `~/.claude/projects` tree each leader generation — `readdir` recursion + a `stat` per file — then filters by mtime and only tail-reads/parses files within `lookbackMs`. That enumeration is O(total transcripts on disk), NOT O(active sessions), so it grows with history — but it's cheap (measured ~33ms readdir + ~3ms stat over ~3.7k files / ~1.1k dirs) and runs on the **leader only** (once per ~5s machine-wide), not per pane; followers do zero disk walk. Directory-mtime pruning to skip dead subtrees is **unsafe** — appending to a transcript does not bump its parent dir's mtime (verified) — so the per-file stat is required. Keep the READ path bounded: tail-by-bytes, never whole multi-MB transcripts, only files within `lookbackMs`. At tens of thousands of files the readdir enumeration will climb (a bounded recent-files index would be the fix); at normal scale the leader tick is under ~140ms and never blocks another pane.

## Conventions

- Modern TS: arrow functions, optional chaining, nullish coalescing, `import type`. Avoid `any`.
- No defensive code for impossible inputs (e.g. negative token counts) — but **do** guard real user-facing paths (e.g. `CCSS_WINDOW=0` is guarded in both `rate.ts` and the config parse).
- Add a test for any new pure behavior; prefer TDD. Keep the e2e fixtures deterministic (fixed `NOW` constant, no wall-clock).
- Surgical changes — match surrounding style.

## Gotchas

- **Never make a render path *wait on* or *kill* ccusage.** The CLI is a node stub that spawns a native binary with inherited stdio and no signal forwarding; ccusage also prints its line *before* it persists its cache. An earlier design awaited ccusage with a timeout and killed it — the killed run orphaned the native grandchild holding a per-session semaphore lock marked in-progress (a verified livelock that froze 🔥/💰 during streaming), and the orphan held our stdout pipe for seconds. The current design sidesteps all of it: the recompute runs fully detached and is never killed or piped (`maybeSpawnCcusageJob`), and every tick only *reads a file*. Keep it that way — don't reintroduce a synchronous ccusage spawn-and-wait.
- **ccusage's offline pricing goes stale at every model launch.** `ccusage statusline` defaults to `--offline`, pricing from a snapshot bundled with the *installed* version. A pre-launch install silently prices a new model's tokens at $0 (this happened at the Fable 5 launch with ccusage 20.0.6: 🔥/💰 under-reported ~4×). When cost segments look implausibly low after a model release, `bun install -g ccusage@latest` before debugging this repo. Don't switch to `--no-offline` — it re-fetches the ~3MB LiteLLM DB on every uncached tick (+2.3s, measured).
- **ccusage needs a real stdin.** `ccusage statusline` errors (`missing field transcript_path`) on a minimal payload — the detached job feeds it the verbatim Claude Code stdin, which always carries the fields it needs. If you smoke-test the job by hand, use a full stdin.
- **State files live in `stateDir()`** (`$TMPDIR` by default, `CCSS_STATE_DIR` to relocate) — `ccss-claim`, `ccss-snap-<cfgKey>.json`, `ccss-limits.json`, `ccss-ccusage.line`/`.job`/`.payload`. Tests point `CCSS_STATE_DIR` at a scratch dir so they never touch the user's **live** files.
- `find`/`tail`/`Date.now` are fine in **this repo's** code; they were only banned in the workflow *script* that generated it.
- The deterministic e2e uses a hardcoded `NOW` epoch and fixture timestamps relative to it (fixture files' real mtimes are after `NOW`, so they always pass the lookback filter). If you change the window math, update the documented arithmetic in `test/e2e.test.ts`.
- The user has an interactive shell alias `ccusage='bunx ccusage daily -b'` — irrelevant here (the status line is non-interactive and we resolve the binary explicitly), but don't be confused by it.
